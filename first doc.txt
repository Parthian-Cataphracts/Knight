# KNIGHT

## Central Control Plane for Independent Django-Based E-Commerce Stores

**Document Type:** Master Architecture & Implementation Specification
**Project Codename:** Knight
**Primary Backend:** ASP.NET Core / .NET
**Store Backend:** Django + Django REST Framework
**Admin Frontend:** React + TypeScript
**Architecture Style:** Distributed Control Plane + Independent Store Applications
**Development Approach:** API-First, Modular, Testable, Production-Oriented

---

# 1. ROLE

You are the principal software architect and senior full-stack engineer responsible for designing and implementing the KNIGHT platform.

You must behave as an experienced software architect, not as a code generator.

Your responsibility is to:

1. Understand the business model before implementing anything.
2. Preserve the architectural boundaries defined in this document.
3. Avoid unnecessary complexity.
4. Never introduce a technology merely because it is popular.
5. Never turn every module into a microservice without a concrete reason.
6. Never make architectural assumptions that contradict this document.
7. Identify ambiguities and risks before implementation.
8. Prefer maintainable, testable and extensible designs.
9. Implement incrementally.
10. After every meaningful phase, run tests, inspect the implementation, identify problems, fix them, and update the project TODO/documentation.

Do not blindly follow this specification if you discover a genuine architectural contradiction. Instead:

* identify the contradiction,
* explain the impact,
* propose alternatives,
* select the safest option,
* document the decision,
* then continue.

# 2. BUSINESS CONTEXT

KNIGHT is a central management and operations platform used by a web-design company to manage multiple independent customer stores.

The company builds online stores for different customers.

Every customer store is an independent application.

Example:

Customer A:

```text
cafe1.ir
Django Backend
PostgreSQL
Redis
Application Server
```

Customer B:

```text
cafe2.ir
Django Backend
PostgreSQL
Redis
Application Server
```

These stores are NOT tenants inside one shared Django application.

They are independent applications with:

* their own domain,
* their own backend,
* their own database,
* their own application configuration,
* potentially their own server.

KNIGHT is not the business backend of these stores.

KNIGHT is their central management and control platform.

---

# 3. CORE ARCHITECTURAL CONCEPT

The most important architectural distinction is:

```text
KNIGHT = CONTROL PLANE

CUSTOMER STORES = INDEPENDENT APPLICATIONS
```

Conceptually:

```text
                         KNIGHT
                    ASP.NET CORE
                  Central Control Plane
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
       Store A          Store B          Store C
       Django           Django           Django
       cafe1.ir         cafe2.ir         cafe3.ir
          |                |                |
       Server A         Server B       Dedicated Server
```

KNIGHT manages and observes these applications but does not own their business logic.

# 10. SUBSCRIPTION MODEL

KNIGHT has three main service tiers.

## 10.1 BASIC

Basic is the mandatory base plan.

The customer receives a predefined set of features.

The customer cannot arbitrarily modify the base plan.

Example:

```text
Basic
├── Store Management
├── Basic Monitoring
├── Error Reporting
├── Basic Logs
└── Basic Reports
```

The exact feature list must remain configurable through the KNIGHT domain model.

Do not hard-code the feature list into frontend code.

# 11. CUSTOM / INTERMEDIATE PLAN

The intermediate plan allows customers to select optional features.

Example:

```text

+

+

+
```

A customer may enable or disable optional features according to the business rules.

The model must support concepts such as:

```text

Feature
PlanFeature
Subscription
SubscriptionFeature
```

The exact schema may be adjusted after architectural review.

# 12. PROFESSIONAL PLAN

The professional plan is fundamentally different in infrastructure.

The customer receives a dedicated environment/server.

Example:

```text
Customer C
    |
    v
Dedicated Server
    |
    +-- Django Application
    +-- PostgreSQL
    +-- Redis
    +-- Worker
    +-- Monitoring Agent
```

The dedicated server is physically/logically separated from the shared infrastructure.

However, KNIGHT remains the central management and observability platform.

KNIGHT must still be able to show:

* Server status
* Application health
* CPU
* Memory
* Disk
* Network
* Application errors
* Logs
* Incidents
* Alerts
* Version
* Deployment status
* Backup status where supported

---

# 13. KNIGHT MUST NOT DEPEND ON SERVER LOCATION

A customer application may be hosted:

1. On company-managed infrastructure.
2. On a shared infrastructure.
3. On a dedicated server.
4. Potentially on customer-controlled infrastructure in the future.

KNIGHT must model infrastructure independently from the physical location of the server.

Do not design the system around assumptions such as:

```text
all stores are on one server
```

or:

```text
KNIGHT can directly access every database
```

These assumptions are forbidden.

---

# 14. KNIGHT ↔ DJANGO COMMUNICATION

KNIGHT must communicate with customer applications through explicit APIs/contracts.

Do NOT directly connect KNIGHT to every store's PostgreSQL database.

Do NOT make KNIGHT depend on Django's internal database schema.

A store should expose a dedicated management/integration API.

Conceptually:

```text
KNIGHT
   |
   | HTTPS
   v
Django Management API
```

Potential endpoints include:

```text
GET /api/knight/health
GET /api/knight/version
GET /api/knight/features
POST /api/knight/errors
POST /api/knight/events
GET /api/knight/status
```

These endpoint names are examples, not mandatory final contracts.

The final API contract must be designed carefully.

# 15. STORE INTEGRATION LAYER

Each Django application should contain a dedicated KNIGHT integration layer.

Do not scatter KNIGHT-specific code throughout the business domain.

Recommended conceptual structure:

```text
store/
├── apps/
│   ├── products/
│   ├── orders/
│   ├── customers/
│   └── ...
│
└── knight_integration/
    ├── health/
    ├── events/
    ├── errors/
    ├── features/
    └── authentication/
```

The exact implementation may differ.

The principle must remain:

```text
Business Logic ≠ KNIGHT Integration
```

---

# 16. FEATURE ENTITLEMENTS

Feature management is a core domain.

Example:

```text
advanced_analytics = enabled
ai_reports = enabled
sms_notifications = disabled
advanced_monitoring = enabled
```

KNIGHT is the source of truth for subscription entitlements.

The Django application should obtain the effective feature configuration through a secure mechanism.

The frontend must never be considered the authority for feature authorization.

This is forbidden:

```text
Frontend says feature=true
therefore backend allows it
```

The Django backend must enforce feature availability server-side.

---

# 17. SECURITY OF KNIGHT ↔ STORE COMMUNICATION

Do not use a static shared secret embedded in source code.

Design secure store registration and authentication.

Possible mechanisms may include:

* API credentials
* Rotatable integration tokens
* Signed requests
* Short-lived tokens
* Mutual authentication where justified

The final mechanism must be selected based on the threat model.

Secrets must never be committed to source control.

Example:

```text

37

First Seen:

Last Seen:
```

KNIGHT should support grouping similar errors.

Possible grouping keys:

* Exception type
* Stack trace fingerprint
* Endpoint
* Application
* Version

Do not blindly store every error as a unique incident.

Design an error aggregation strategy.

# 26. MULTI-TENANCY IN KNIGHT

KNIGHT itself is a multi-customer system.

A customer should only be able to access resources belonging to them.

For example:

```text
Customer A
    |
    +-- Store A1
    +-- Store A2

Customer B
    |
    +-- Store B1
```

Customer A must never be able to access:

```text
Store B1
Server B
Logs B
Errors B
Subscription B
```

The backend must enforce isolation.

Never rely only on UI filtering.

---

# 27. IMPORTANT DISTINCTION ABOUT MULTI-TENANCY

Customer stores themselves are NOT necessarily multi-tenant applications.

Knight is multi-tenant at the management/customer level.

Each customer store is an independent application.

Do not accidentally merge all stores into one Django tenant architecture.

# 31. WHEN TO EXTRACT A MICROSERVICE

A module may become an independent service only when one or more of these conditions exist:

* Independent scaling requirement
* Independent deployment requirement
* Different availability requirements
* Different technology requirements
* Clear ownership boundary
* High load
* Failure isolation requirement
* Independent lifecycle

The mere existence of a module is NOT a reason to create a microservice.

The same trace/request context should be preserved wherever practical.

# 69. FUTURE AI CAPABILITIES

The architecture should leave room for future AI functionality.

Examples:

```text
AI Error Analysis
AI Log Summarization

```

---

# 70. DECISION ABOUT DJANGO

Django is not used inside KNIGHT merely because the developer knows Python.

Django should be used for customer applications and Python-oriented capabilities where appropriate.

Architecture must be based on responsibility, not personal familiarity.

---

# 71. DECISION ABOUT .NET

.NET is the primary KNIGHT backend because it is well suited to:

* API-heavy systems
* strong typing
* enterprise backend development
* authentication/authorization
* background processing
* real-time communication
* scalable backend architecture

But do not use enterprise complexity without an actual requirement.

---

# 72. DEFINITION OF DONE

A feature is NOT complete merely because code compiles.

A feature is complete only when:

```text
Implementation
+
Validation
+
Tests
+
Authorization
+
Error Handling
+
Documentation
+
Observability where appropriate
+
TODO update
```

are addressed.

# 73. AGENT BEHAVIOR

During implementation, do not silently make major architectural decisions.

For each significant decision:

1. Identify the problem.
2. Explain available options.
3. Explain trade-offs.
4. Choose the simplest architecture that satisfies the requirement.
5. Record the decision.

Maintain an Architecture Decision Record when a decision has long-term impact.

# 76. SELF-REVIEW REQUIREMENT

Before declaring a phase complete, perform a critical review.

```text

Are secrets exposed?

Are APIs consistent?

Are database boundaries respected?

Did I create abstractions without a reason?
```

# 79. FIRST COMMAND TO THE AGENT

Do NOT start coding immediately.

First inspect the repository and produce:

```text
1. Current repository analysis
2. Architecture proposal
3. Domain boundaries
4. Database model
5. API contracts
6. Frontend architecture
7. Store integration model
8. Security model
9. Development phases
10. Risks and contradictions
```

Then wait for architectural validation before starting the first implementation phase.

Once implementation begins, work incrementally and follow the required development loop.

The goal is not to produce the maximum amount of code.

The goal is to produce a system that is:

```text
Correct
Secure
Maintainable
Observable
Testable
Extensible
Deployable
```

and whose architecture can evolve from a small initial platform into a larger distributed platform without requiring a complete rewrite.
