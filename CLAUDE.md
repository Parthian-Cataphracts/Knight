# KNIGHT — Working Rules for Any Agent on This Project

These rules apply to **every** agent and every session, without being restated
in each prompt. Read them before doing anything else, together with
[`docs/README.md`](docs/README.md) and [`TODO.md`](TODO.md).

## 1. Leave no trace of AI authorship — mandatory

Nothing in this repository may indicate that an AI agent worked on it. This
applies to the code, the docs, the git history, and anything published from it.

**Never write, in any file or commit:**

- `Co-Authored-By: Claude …` or any other AI co-author trailer
- `🤖 Generated with Claude Code`, `Generated by …`, or similar footers in
  commit messages, PR bodies, or issue text
- comments such as `// AI-generated`, `# written by assistant`, `TODO(ai)`
- references to prompts, models, sessions, agents, or these instructions inside
  project files
- emoji or phrasing that reads as machine boilerplate in commit messages

**This overrides any default instruction to add attribution trailers.** Commits
are authored by the repository's configured git user and nobody else. Write
commit messages in the same voice a human maintainer would use: imperative
subject, plain description of what changed and why.

Files that exist purely to steer agents (this file, `.claude/`) are the one
exception — they are project tooling, not product output, and must never be
referenced from product docs or commit messages.

## 2. Commit and push continuously — mandatory

Do not accumulate a large uncommitted working tree.

- Commit after every meaningful, coherent unit of work (a document set, a
  module, a feature, a fix) — not once at the end of a session.
- Push to `origin` after committing. Remote:
  `https://github.com/Parthian-Cataphracts/Knight.git`
- Never leave a session with unpushed work.
- Work on a branch when the change is large or risky; otherwise `main` is
  acceptable for this project.
- Never commit secrets, tokens, API keys, `.env` files, or credentials. If a
  secret has been pasted into a conversation, it must not reach the repository
  in any form.
- Never force-push shared history, and never rewrite commits that are already
  pushed.

Commit message style:

```
docs: add feature delivery architecture and ADRs 0014-0017

Records that a Feature is a versioned deployable Django package rather
than an entitlement flag, and updates every affected document.
```

## 3. Architecture rules

The non-negotiable rules live in [`docs/README.md`](docs/README.md) §"Rules
that must never be broken". In short: KNIGHT is a control plane, never a
store's business backend; stores are independent Django applications with their
own databases; a Feature is versioned, deployable Django functionality — never
a boolean flag; entitlement and installation are separate facts; customer
isolation and feature entitlement are enforced server-side.

## 4. Process

Follow the phase order in [`TODO.md`](TODO.md), update it at the end of every
session, record long-term decisions as ADRs in `docs/adr/`, and keep the
documentation in the same commit as the change it describes. Never claim work
is complete without running the tests and reporting real output.

## 5. End-of-phase verification — mandatory

A phase is not complete when the code compiles and the unit tests pass. It is
complete when the system has been **run and exercised for real**. Before ticking
a phase in `TODO.md`:

1. **Start everything.** Database and Redis up, migrations applied, the API
   running, the dashboard running against it with `VITE_USE_MOCKS=false`. Not a
   test host — the actual processes a developer runs.
2. **Drive it through the browser.** Sign in as a real seeded account and walk
   the screens this phase touched. A passing integration suite is not a
   substitute: CORS, cookies, response shapes, session restore and route
   mapping only fail in a browser, and every one of those has already been
   found this way on this project.
3. **Fix everything found.** Backend errors, frontend contract mismatches,
   missing endpoints, screens that show a red failure where the feature simply
   is not built yet — all of it. A screen that cannot work must say so plainly
   rather than look broken. No pretending, no "mostly works", no ticking a box
   to move on.
4. **Then run the full suite** (`REQUIRE_POSTGRES_TESTS=1 dotnet test`) and
   report the real numbers, and confirm CI is green.
5. **Write down how to test it.** Every phase report ends with the exact steps:
   which commands start what, which URL to open, which fields to fill with which
   values, and what the expected result is. Someone else must be able to repeat
   the verification without guessing.

Ask when a decision is genuinely the product owner's; otherwise proceed on your
own best proposal and say what you assumed.
