## What KNIGHT is (the problem)

KNIGHT is a **central control plane** that manages many **independent customer
stores**. Each store is its own application, with its own domain, database and
deployment. KNIGHT registers merchants, bills them, provisions their store,
observes its health, and — the hard part — **delivers versioned software Features**
into the stores their customers are entitled to. KNIGHT is never a store's own
business backend.

Direction (2026-08-31): a **self-service SaaS** — a merchant registers publicly,
pays, and gets a fully provisioned, entitled store with no manual operator step.

### Requirements that actually shape the design
- **Multi-tenant isolation** — one customer must never see or touch another's data;
  enforced server-side, failing closed.
- **Entitlement ≠ installation** — being allowed to have a Feature and actually
  having it deployed are separate facts, tracked separately.
- **A Feature is a versioned deployable package**, not a boolean flag — installed,
  upgraded and rolled back per store.
- **Self-service provisioning** — payment must drive provisioning automatically.
- **Auditability & observability** — who did what, and is every store healthy.

## Architectural pattern

**Chosen: a modular monolith control plane + independent per-store apps + external
feature-services.** The control plane is one deployable ASP.NET Core application
split into enforced modules (`Customers`, `Stores`, `Subscriptions`, `Plans`,
`FeatureRegistry`, `FeatureDelivery`, `Provisioning`, `Servers`, `AccessControl`,
`Billing`, `PlatformBilling`, `Ingestion`, `Observability`, `Onboarding`,
`AutoAdmin`). Stores are separate apps. Heavier Features ship as their own
`external_service` processes reached over a signed proxy.

**Why:** the control-plane concerns share one database and many transactions
(a checkout grants entitlements, which queue provisioning, which installs
Features) — a modular monolith keeps those consistent and simple to run, while the
module boundaries (enforced by architecture tests) stop it becoming a big ball of
mud. The genuinely independent, scalable, or language-different work (a store, an
analytics service) lives *outside* the monolith where it belongs.

**Rejected: full microservices for the control plane.** It would scatter one
naturally-transactional workflow across network calls and distributed
transactions, buying scaling the traffic doesn't need at the cost of consistency
and operability. The seams that *should* be separate processes (stores, feature
services) already are.

## Tech stack (with the "why")

| Layer | Choice | Why |
|---|---|---|
| Control-plane API | **.NET 10 / ASP.NET Core** | one strongly-typed, transactional monolith; mature EF Core + DI + hosted workers |
| Persistence | **PostgreSQL + EF Core** | relational integrity fits entitlements/subscriptions/installations; a `control` schema isolates it |
| Dashboard | **React SPA (Vite, react-i18next, zustand)** | operator + merchant portal; RTL/Persian-first; talks to the API over `/api/v1` |
| Stores | **Independent Django apps** | each tenant isolated with its own DB/domain; KNIGHT delivers Features into them |
| Feature services | **FastAPI (Python) `external_service`** | per-feature processes behind an HMAC-signed proxy; scale/deploy independently |
| Async work | **hosted `BackgroundService` workers + durable outbox** | provisioning, delivery, event forwarding survive restarts |
| Auth | **JWT + refresh rotation, TOTP MFA for staff** | platform vs. tenant principals, permission-gated |

Layering inside the API: `Knight.Api` (endpoints) → `Knight.Application` (ports) →
`Knight.Domain` (aggregates) with `Knight.Infrastructure` implementing the ports;
`Knight.Contracts` holds the wire types. Dependencies point inward only (enforced
by architecture tests).

## Roadmap

- **Phase 1 — MVP (built):** control-plane core (customers, stores, credentials,
  isolation), feature registry + delivery, provisioning engine, observability,
  self-service register→verify→checkout→pay→provision, Persian portal. *Done when a
  stranger can sign up, pay, and reach an Active store — verified in a browser.*
- **Phase 2 — Advanced (largely built):** the Feature catalogue (~16 real
  `external_service` Features), Automatic Admin family, rollouts, alerts/incidents,
  in-product help. *Done when Features install per-entitlement and the store serves
  them.*
- **Phase 3 — Scale/harden (open, owner-gated):** real store hosting for arbitrary
  signups (wildcard DNS/TLS + per-store deploy — today simulated on a `.local`
  domain), real payment gateway (today simulated), real SMTP (today logs the link),
  Automatic-Admin AI keys/channel tokens, security review, backup custody, release
  call. *Done when a paying stranger gets a real public shop.*
