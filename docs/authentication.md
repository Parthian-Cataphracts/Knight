# Authentication

Status: **authoritative proposal**.

KNIGHT authenticates three fundamentally different principal types. They never
share credentials, tokens, or policies.

```
principal_type: user | store | agent
```

## 1. Human users (dashboard)

- Email + password login. Passwords hashed with a memory-hard algorithm
  (Argon2id preferred; the existing `IPasswordHasher` abstraction stays).
- Short-lived **JWT access token** (~15 min) + long-lived **refresh token**
  (rotating, one-time use, stored hashed, bound to a `Session`).
- Refresh-token reuse detection revokes the whole session family.
- Claims: `sub`, `principal_type=user`, `customer_id` (absent for platform
  staff), `roles`, `session_id`, `env`. Permissions are resolved server-side,
  not trusted from the token.
- MFA (TOTP) is required for platform staff with `SuperAdmin` or `Admin` roles.
  Modelled from the start (`User.mfaEnabled`), enforced from Phase 2.
- Tokens are stored in memory in the dashboard, with the refresh token in an
  `HttpOnly`, `Secure`, `SameSite=Strict` cookie. No tokens in `localStorage`.
- Lockout and rate limiting on the `auth` policy after repeated failures.

## 2. Stores

See [`adr/0012`](adr/0012-store-authentication-mechanism.md).

```
clientId + clientSecret   (long-lived, rotatable, hashed at rest)
        │  POST /api/v1/ingest/handshake
        ▼
short-lived store token   (~30 min, scoped to one storeId + environment)
        │
        ▼
used for all ingestion calls
```

- The secret is generated by KNIGHT, shown once, and stored only as a hash.
- Rotation issues a second active credential; both work during a grace window,
  then the old one is revoked. Rotation is a first-class dashboard action.
- The handshake validates: credential active, store active, customer active,
  environment match, and (optionally) source IP allow-list.
- No shared secret is ever embedded in source control or a Docker image.
- Requests may additionally be signed (HMAC over method+path+body+timestamp+nonce)
  to defend against replay on ingestion endpoints; nonces live in Redis.

## 3. Agents

- Provisioned with a **one-time provisioning token** tied to a `Server`.
- The handshake exchanges it for a long-lived agent token stored hashed, bound
  to `agentId` + `serverId`.
- Agent tokens grant `agent.report` and `agent.executeJob` for **their own
  store only** — they can report telemetry and claim/execute lifecycle jobs,
  and can read nothing else in KNIGHT.
- Each job additionally carries a short-lived, single-job token; it is bound to
  one `jobId` and expires with the job. Package downloads use it too, so a
  leaked artifact URL is useless on its own.
- A revoked or unknown agent token yields `401` and raises a security alert.

## 4. What each principal may do

| | Dashboard API | Ingestion API | Agent API |
|---|---|---|---|
| user | yes (permission-checked) | no | no |
| store | no | yes, only its own store | no |
| agent | no | no | yes, only its own server (telemetry + its own jobs) |

Cross-type access is rejected at the policy layer, before any handler runs.

## 5. Token handling rules

- Signing key comes from configuration/secret store; never from source.
- Asymmetric signing (RS256/ES256) is preferred so verification can later be
  distributed; symmetric is acceptable while everything is one process.
- Clock skew tolerance is small and explicit.
- Every token includes `env`; a token minted in one environment is invalid in
  another.
- All authentication outcomes (success, failure, lockout, rotation, revocation)
  are audited without recording the credential itself.

## 6. Reuse from existing code

`modules/Identity` already implements password hashing, access-token
generation, refresh-token rotation, and sessions
(`docs/adr/0006-refresh-token-rotation-and-session-strategy.md`). It is kept
and extended with `customerId` scoping, MFA, and the store/agent principal
types.

## Account invitations

A new administrator receives an activation link by email and chooses their own
password; nobody else ever learns it. The link carries a token whose hash is all
KNIGHT stores, it works once, and it expires (two days by default) — an
invitation that never expired would be a permanent way into an account nobody
has claimed.

Where a deployment has no mail transport configured, account creation falls back
to the one-time password it always had: generated, returned exactly once, and
never readable afterwards. The response says which of the two happened, so an
operator is never left guessing whether to read a password out or wait for a
mail. `POST /api/v1/auth/activate` completes an invitation and is anonymous by
nature, rate-limited on the same policy as login.
