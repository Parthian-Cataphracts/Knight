# 0012 — Store authentication via rotatable credentials and short-lived tokens

- Status: **Proposed**
- Date: 2026-08-18

## Context

KNIGHT and each store exchange telemetry and entitlements across networks that
KNIGHT does not control. Stores may sit behind NAT, may be customer-managed,
and may be numerous. The specification forbids a static shared secret in source
code and requires rotatable credentials.

## Options considered

1. **Static shared secret** — forbidden; unrotatable, leaks permanently.
2. **Long-lived per-store API key on every request** — simple, but a leaked key
   is valid until someone notices, and it travels on every call.
3. **mTLS** — strongest, but certificate distribution and renewal across
   customer-managed servers is operationally heavy for the current scale.
4. **Client credentials → short-lived token**, optionally with request signing.

## Decision

**Option 4.** Each store receives a `clientId` + `clientSecret` (generated by
KNIGHT, displayed once, stored hashed). The store exchanges them at
`POST /api/v1/ingest/handshake` for a store token (~30 min) scoped to one
`storeId` and one environment. Ingestion endpoints accept only that token.

Additional controls: rotation with a dual-active grace window; immediate
revocation; environment binding enforced at handshake; optional IP allow-list;
optional HMAC request signing with timestamp + Redis nonce for replay
protection on ingestion endpoints; per-store rate limits.

mTLS remains the upgrade path for dedicated/professional infrastructure and can
be added per store without changing the contract.

## Consequences

**Positive** — a leaked token expires quickly; a leaked secret is revocable and
rotatable without redeploying the store; every call is attributable to one store
and one environment; works through NAT because all connections are outbound
from the store where needed.

**Negative** — one extra round trip per token lifetime and token caching logic
in the integration layer; KNIGHT must keep a token issuance path highly
available or stores buffer telemetry.

**Follow-up** — decide the signing algorithm and key rotation procedure
(`risks.md`), and whether IP allow-listing is practical for customer-managed
hosting.
